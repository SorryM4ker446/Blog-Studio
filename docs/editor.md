# Article editing and publication

The editor reads complete articles through authenticated `GET /api/admin/posts/:id`. Article details and successful writes include a positive `version`; list and search summaries remain body-free. Existing article URLs use `edit=ID`, while new articles use `edit=new`.

## Content list pagination

Posts, Files, and Links in Content Editor use single-column management lists with aligned metadata and a bottom pagination row. A post title opens the public article when published and the editor when drafted; a file name opens its preview. Each row's More menu contains Edit and Delete, plus Download for files; link rows also keep adjacent order controls. Rows reveal a short left accent line and a soft tint that fades out toward the middle on pointer hover; both fade in and out without changing the row background. Opening the menu keeps its row highlighted; other rows also highlight normally when hovered. More controls respond to pointer hover, while keyboard focus uses an outline. It closes on Escape, focus moving outside, or a pointer press outside, and opens above the row when there is too little room below. The menu fades and shifts on open and close, with immediate changes when reduced motion is requested. File types appear as format names instead of raw MIME strings, using the saved MIME and original extension. Delete still requires confirmation. Page changes let the old rows exit before new rows enter with a short directional fade. A multi-page result reserves ten row slots for Posts/Files or eight for Links, including a short last page opened directly. Rows are 76px high on wide screens; narrower layouts reserve the height needed for their metadata and controls. The column headings and reserved height adapt together. A result that fits one page uses its actual row count, and empty results use the normal empty state. Link destinations, status, order and actions stay aligned in their own columns on wide screens.

Existing rows and pagination remain visible during explicit paging. A cold return uses the target URL's server data when it matches, otherwise a stable loading area with the target page. Failures offer retry without showing rows from an unrelated page. Background revalidation commits a complete response; obsolete navigation, account or session work cannot update the current result. Deletion can replace an exhausted page with the last valid page through a bounded correction. Reduced motion disables result animations. All Posts and Cloud Drive retain their natural content heights and bottom controls; advanced search keeps independent Posts/Files pages and its existing responsive arrows.

Creating a post, file or link briefly fades the new row in; existing rows displaced by insertion move into place. The new row also borrows the list's left-side hover glow and accent line for a short entrance, then clears that highlight. Files enter after the upload dialog exits. Deleting a row fades it out while surviving rows close the gap; deleting the last row fades it without a list jump. Reduced motion applies these changes immediately.

## Explicit actions

| Action | Request | Behavior |
| --- | --- | --- |
| Create a draft | `POST /api/admin/posts` with title, content and optional editable fields | Always creates a draft at version 1; requesting published status is rejected |
| Save | `PUT /api/admin/posts/:id` with `version` and editable fields | Saves content without changing publication status |
| Publish | `POST /api/admin/posts/:id/publish` with `version` and optional editable fields | Atomically saves supplied fields and publishes a draft |
| Draft (withdraw publication) | `POST /api/admin/posts/:id/unpublish` with only `version` | Withdraws publication without saving pending form edits |

All actions require administrator authentication and CSRF protection. Ordinary updates reject a supplied `status`; use the dedicated action endpoints. Category ID `0` clears the category. Missing, fractional, negative or otherwise invalid versions return HTTP 400. Unknown resources return 404. A stale version returns HTTP 409 with `code: post_version_conflict`; an incompatible publication state returns 409 with `code: post_state_conflict`. Clients must not automatically retry conflicting writes or substitute a newer version into an old payload.

The form displays a compact publication badge and separate `Save` and `Publish`/`Draft` controls. Enter submits an ordinary save. `Save` always stays in the current editor, for both drafts and published articles; only a successful `Publish` returns to Content Editor. `Draft` withdraws publication through the existing unpublish API and remains in the editor. Pending writes lock editable controls and duplicate submissions. Clicking Save without changes does not send a write, even after another action fails; a failed save with unsaved changes remains retryable. Editing a field clears feedback for the previous form state. The Save button keeps its label, dimensions, colors and opacity throughout the request; a separate live status reports progress. Save feedback appears as a quiet inline status beside the Markdown field label and wraps beneath it on narrow screens. It fades in on arrival and fades out after editing resumes, with the narrow-screen space collapsing smoothly; reduced motion changes it immediately. Success and errors retain their status and alert roles. Saved timestamps and a subtle `View article` text link with a diagonal arrow remain available for published articles. The link keeps the same in-tab navigation and editor return target.

`View article` opens in the current tab. Its URL carries a local `returnTo` editor URL matching the article ID, preserving the source list filters. The page Back button returns directly to that editor; browser Back also returns through history. Return targets outside the matching editor are rejected. Ordinary article links retain history-based return, with All Posts as the fallback when no history exists.

Viewing uses the same browser recovery copies as other departures. Unsaved input prompts before leaving; on return, restore a copy, discard it, or keep it and continue with the current version.

Publishing a new article first creates a draft, then publishes that ID and version. If publication fails after draft creation succeeds, the editor retains the draft ID and updates its URL, so a retry does not create another article. If the creation response itself is lost, the outcome is uncertain: check the content list before retrying creation. The client does not automatically repeat creation requests after network failures.

## Changes and conflicts

Dirty state compares title, introduction, Markdown and category with the last successfully loaded or saved snapshot. Restoring the original values clears the dirty state. Preview changes and category-list refreshes do not alter the snapshot. Unpublishing updates the saved status/version while retaining pending form edits, which remain dirty until saved.

On conflict, the current text remains editable and write actions are disabled. The themed review card offers `Review saved version` (then `Refresh saved version`) to fetch a read-only server preview without changing the form. Refresh keeps its label and appearance steady while the request is pending. After reviewing, choose `Keep my edits and continue` to retain all local fields and explicitly adopt the reviewed server version as the new baseline, or `Discard my edits and use latest` to replace both fields and baseline. The review card fades out and collapses after either choice; reduced motion removes it immediately. Neither choice saves or publishes. Keeping edits does not merge server changes: the next Save replaces the reviewed server fields with the current form. Normal version checks still apply; a further concurrent change blocks the write again and clears the obsolete preview so a new review is required. Browser recovery records the retained fields against the adopted version. The layout wraps actions on small screens.

Article mutations and conflict-detail reads handle HTTP 401 locally to avoid redirecting away from entered text. Sign in in a new tab, return to the original editor and retry. This does not bypass server authentication, authorization or CSRF checks. Other protected requests retain the normal session-expiry behavior.

## Persistence and deployment boundaries

Migration `2026090901` adds `posts.version` and a PostgreSQL update trigger. Historical articles start at 1 without changing their content or timestamps. Every row update advances the version, including foreign-key updates when a category is deleted; these category changes do not rewrite article timeline timestamps. Conditional writes and response reloads run in one transaction, so a failed reload rolls back the write and its version change. The maximum supported version is JavaScript's maximum safe integer, 9007199254740991.

Deploy frontend and backend together, apply pending migrations before API startup, and reload old clients: writes without versions are incompatible. See [deployment](deployment.md) and [backup and restore](backup-restore.md); image-only rollback across a new migration is unsupported.

## Browser recovery copies

IndexedDB's schema version and each record's format version are independent of article versions. Unsupported or malformed records are never restored.

The browser stores unsaved title, introduction, Markdown and category fields in IndexedDB, together with a format version, user ID, article or new-draft identity, original saved fields/version, and timestamps. Copies expire after seven days. Writes are throttled to at most one per second during continuous input, with a best-effort flush on visibility loss, navigation and unload. Each article and each new-draft identity can retain up to three copies. The total count therefore grows with the number of article and draft targets; when a fourth copy arrives for one target, its oldest copy is removed, without removing copies for other targets. Existing stores with more than three copies for a target are trimmed when those copies are discovered. A separate 10 MB (10,000,000 bytes) encoded-data limit applies per origin; writes over that limit fail without evicting another target's copies. Expired or malformed copies are removed during discovery; the editor reports skipped copies and storage failures in a compact status above the editor. That status fades in and out while its space opens and closes smoothly; reduced motion changes it immediately. Storage failure never prevents manual server saving.

Existing article copies are offered only for that article and authenticated user. `edit=new` receives an independent `draft` URL identifier. New-article entry also offers this user's unfinished new drafts, so closing the original tab does not make them undiscoverable. Choosing one forks its fields into the current new-draft identity. Browser copies do not create articles or upload files. Referenced uploads may have been deleted independently; inspect previews and replace missing references before saving.

Each editing session writes a unique copy key. A sessionStorage ownership identifier survives same-tab reloads; Web Locks separate ownership when a tab is duplicated. Without Web Locks, a fresh document owner is used conservatively: copy keys remain isolated, but source copies from earlier documents require explicit discard rather than automatic same-tab cleanup. Restoring a copy does not create another copy if its content, baseline and article version remain identical; the existing source is checked in the same storage transaction, so a missing source is backed up again. Editing or adopting a newer server version creates a separate copy while preserving the source. Saving the fork keeps a source from another tab, but clears the specifically restored source when it belongs to this tab. Other unselected copies are retained, including same-tab alternatives; explicit discard removes the listed copies only after storage confirms deletion. A failed discard keeps the recovery choices visible for retry. Unpublishing preserves pending text and advances its recovery baseline to the returned version. Reverting fields to the saved snapshot also clears the current copy.

Restore, discard and Keep copies and continue are explicit choices; none writes an article to the server. A restored old version is never silently replaced with the latest version. When the version differs, the editor keeps the local text and enters the existing conflict review flow with the latest server content available for comparison. There is no automatic publishing, conflict merge or force overwrite.

The recovery panel follows the current light/dark theme, lists each copy's title and timestamp, and provides an individual Restore action and a separate discard action. The form remains locked while recovery discovery or a version choice is pending, and its status explains the lock. After a choice, the panel fades out and collapses so the form moves up smoothly; reduced motion removes it immediately. Restoring a copy shows a brief inline `Draft restored` status beside the Markdown label; editing again fades it out. This feedback does not mean the copy was saved to the server. Keep copies and continue unlocks the current server version (or empty new draft) without restoring or removing stored copies. Later edits use a separate copy; saving does not remove copies kept by this choice, even when they came from this tab. They remain available on a later visit until explicitly discarded or expired. Discard buttons stay locked until cleanup completes.

Reloading a previous recovery notice keeps its heading, copy titles, timestamps, count and paused status visible while IndexedDB discovery runs, without skeletons or loading labels. Presentation hints in the current browser history entry retain notice heights and up to three titles and formatted dates, scoped to the same URL, user and viewport. They contain no article bodies, copy IDs or recovery choices. These labels are presentation only: inputs and recovery actions remain locked until actual discovery and layout adjustment finish. Missing, malformed or stale hints use the current server layout; actual discovery reconciles expired or removed copies and reports storage failure separately. Saved articles and empty new drafts show their server-known status immediately, and the published article link remains visible throughout. A newly discovered recovery choice changes the status to `Editing paused · Browser recovery` once. Reloading a conflict retains its previous notice space, then transfers that space to the recovery panel over 440 ms. The new panel fades in with a small upward movement after expansion starts, keeping its content from appearing abruptly through a narrow clip. Actions become available only after both layout and entrance animations finish; an explicit recovery choice is still required. Restore opens version review while the recovery panel collapses, with coordinated height and opacity transitions; reduced motion changes the layout immediately. Reload resets page and editor input/preview scrolling to the top; history traversal retains its recorded content position.

Successful logout cancels local pending writes, clears all of that user's copies for the origin and advances a persisted user generation. Other tabs receive a logout notification, clear their authenticated state and cancel pending recovery work; any old writer generation is refused even if notification is unavailable. Per-copy removal markers and serialized writer operations prevent delayed writes from resurrecting cleared records. Failed logout retains copies. Session expiry preserves the current copy before an application redirect; article write failures continue to offer signing in in another tab. Different users never receive each other's recovery choices.

These are unencrypted local working copies, accessible to scripts running on this origin and people with access to the browser profile. They contain no passwords, session Cookies or CSRF tokens, are not sent to the server by the recovery module, and are not included in server backups. Browser eviction, clearing site data, private browsing, unavailable storage and forced process termination can remove them. If local deletion fails after a confirmed server logout, the application warns that site data must be cleared before sharing the browser. Changing the site's scheme/host/port creates a different browser storage origin.

Closing all Incognito/InPrivate windows can discard the private session's IndexedDB, even when a recovery write has completed. Signing in again cannot restore that browser-local data. Save to the server before ending a private session if the changes must survive; use a normal persistent browser profile when testing recovery across browser restarts. See [IndexedDB storage and private browsing](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Basic_Terminology).

## Leaving the editor

Dirty forms open a themed confirmation before returning to the content list, following ordinary same-tab links (including View article and sidebar links), application router navigation, and Back/Forward within application history. The panel and backdrop fade in together and finish their exit before a confirmed departure; cancelling also fades out before focus returns. Reduced motion closes immediately. Stay in editor is focused initially; Tab cycles through the dialog buttons, and Escape cancels and restores focus without scrolling. Cancel keeps the form and framework history state. Repeated requests cannot replace the pending destination. Leave editor flushes browser recovery before replaying the chosen action. If recovery is already known to be unavailable or full, the dialog warns before the user chooses Leave anyway; an unsuccessful final write still allows that informed departure. If an unexpected failure occurs only during the final write, the dialog shows the warning and requires a second leave choice. Changing editors, session expiry or logout invalidates a pending decision and any late completion.

Stay in editor and Escape remain available while a recovery flush is pending. Cancelling invalidates that continuation, so slow storage cannot force a later departure.

The navigation module installs before hydration, adds only its own history position marker and preserves all router state fields. A guarded history traversal first returns to the current entry before opening the asynchronous confirmation, suppressing both tentative events from the router and scroll-restoration listeners. Acceptance replays the original traversal once; cancellation adds no synthetic history entry. New-tab/modifier-click links, downloads and same-document fragments retain their native behavior. Pending article writes block application departures until completion.

Collapsing or expanding the sidebar is a layout action: it does not navigate, prompt to leave, submit the article, or replace the editor. The sidebar keeps its navigation nodes mounted and uses a shared easing curve. When surrounding components wrap into new rows, a separate position-animation module softens the jump; it does not scale text or change article-body sizing rules. Motion can reverse before completion, is cleaned up on navigation, and is disabled by the system's reduced-motion preference. Browsers without the component animation API retain the CSS sidebar transition and normal responsive layout.

The desktop editor detail frame uses a viewport-based width budget calculated from the expanded sidebar, capped at 1200px, in both sidebar states. Its header, recovery panel, fields and Markdown editor move together without changing width when the sidebar toggles. At widths of 768px or less, the editor uses the available content width and stacks Markdown input/preview. Mobile navigation is a separate modal drawer; cancelling an editor departure retains the drawer and focused link. See [mobile and keyboard behavior](accessibility.md).

Refresh, tab closure and departures to another document use the browser's native unsaved-changes prompt. Websites cannot theme this browser UI, add a recovery-capacity warning to its text, or replace it with an asynchronous app dialog. A known recovery failure remains visible above the editor before refresh. The prompt's wording and availability are browser-controlled and normally require prior interaction. Browsers can suppress prompts, especially on mobile or forced termination; asynchronous storage work is not guaranteed to finish during unload. Regular throttled copies reduce this risk but are not a zero-loss backup guarantee. Application program navigation must use `useEditorRouter` or pass the intended continuation to `requestEditorNavigation`; external scripts that bypass these entry points are outside the application contract.

## Rendering and navigation

List return snapshots are optional browser-memory optimizations, isolated by user for protected data and bounded to 20 entries and five minutes. Logout and session expiry clear them. They contain no unsaved article text. Matching server-rendered data or a target-page loading area works without a snapshot. Client route entry revalidates even when its server snapshot already matches the URL; errors remain visible and retryable.

The URL owns page numbers, query, category, scope and resource tab. Each history entry has its own validated identifier, URL and scroll offset; article entries also retain their source selection and return target. Writes preserve Next.js and editor departure-protection fields. Two visits to the same URL do not share scroll state. Refresh and ordinary history restoration use this metadata without sessionStorage. Direct article entry still defaults to All Posts when there is no valid source.

Content Editor no longer measures or stores list dimensions. The obsolete sessionStorage layout record is removed on document entry, and the head bootstrap no longer generates dimension rules. Its remaining responsibilities are source highlighting and initial scroll restoration. Refresh is silent; returning from detail keeps whole-page entrance without replaying pagination. Explicit paging and searching retain their existing transitions. Submitting a new Editor search starts at the top of the content scroller, including when a previous query is submitted again; browser history traversal still restores the saved offset for its entry.

The content scroller saves offsets before departures and restores them after the target layout commits. Delayed content can be retried for at most two seconds, after which browser clamping determines the reachable offset. Wheel, touch, pointer and scroll-key input cancel restoration; navigation and unmount clean up pending callbacks. Input before hydration also cancels the later takeover. Changed server content may shorten a public list or remove an item, so restoration does not promise an unchanged historical content snapshot.

Older history entries without per-entry metadata start without a saved offset. Browser history loss loses both the source and position.

Posts/Files tabs share a sliding selection background. Explicit tab, category and search changes retain the previous results until the requested response is available, then run the existing scope exit/entrance transition. Empty results participate in the same transition. Response criteria stay paired with their rows, including inactive tabs' server snapshots; an older response cannot label rows with a newer query. Pagination keeps its separate motion, and scope changes do not replay a page animation. Narrow toolbars wrap complete controls rather than splitting tab labels. Reduced motion commits the result without animation.

The first successful draft save changes its recovery target from the browser draft to the new article ID. Native history can change before React commits the new search parameters. The form adopts the saved ID when those parameters arrive, retaining its saved fields throughout that interval instead of resetting and fetching the same article again. Recovery discovery and input locking remain active; checking uses the existing status row without inserting a row above the form.

An already resolved empty list remains an empty result while a search, category change or background refresh is pending. It is not replaced with a visible Loading label. Explicit criteria changes transition directly from the previous result to the new result; a cold entry without matching data still uses its bounded loading area and failures remain retryable.

Direct editor URLs and refreshes receive the requested article from the authenticated server endpoint. The form and Markdown input/preview render on the server and hydrate in place. The Markdown wrapper seeds the upstream editor's initial preview using the same synchronous renderer as subsequent edits. Missing or failed initial detail reads retain the existing cancellable loader and retry path. Server details are used only for the matching URL and original authenticated owner. A local view boundary animates list/detail switches once; first saves keep the same detail view and document refresh does not replay an entrance.

The Markdown library detects browser language at import time, whereas its server default is English. Initialization explicitly uses that same default for hydration. After mount, the library restores the supported browser language and the wrapper refreshes its cached toolbar elements without changing their keys or replacing the editor. Chinese tooltips remain available; locale selection does not produce mismatched server/client attributes or require suppressing hydration warnings.

The category-add button keeps its normal opacity while recovery discovery or saving disables the enclosing form. It remains disabled and excluded from interaction until the lock clears. Explicitly unavailable category actions retain their ordinary disabled presentation outside that form-wide lock.

The inline category-create row expands and collapses on Create and Cancel. Successful rename updates the selected category from the server response without replacing the whole dropdown; moving into its management controls clears any unrelated option highlight.

## Homepage links

The **Links** resource tab (`/editor?tab=links`) manages homepage shortcuts independently of posts and cloud files. New and updated links have a title of up to 25 characters and a description of up to 50 characters. The form shows live character counts beside both fields. Existing longer values remain readable but display an over-limit warning and must be shortened before saving an edit. Each link also has a destination (2,048 bytes), a built-in icon, a preset or custom color, visibility and display order. A hidden link may have no destination; visible links require an absolute HTTP or HTTPS URL without embedded credentials. Destinations are stored in PostgreSQL, not in frontend code. External links open a new tab with `noopener noreferrer`.

The editor shares the persistent tab shell, search transitions and pagination animation with Posts/Files, as well as their primary-action styling. Its initial authenticated server response includes links on every editor tab, so counts and direct Links entry render before hydration. Ordinary tab changes reuse the resolved session list, including empty results, without another read. Initial read failures, explicit error retries and entry after an unsuccessful write fetch current data; a document reload also refreshes the server snapshot. Changes made in another editor session are not automatically fetched by an ordinary tab switch. Sorting keeps the current page and list height stable. Cross-page moves fade the outgoing row before the incoming row appears. Same-page moves fade and shift the two swapped rows individually while other rows stay still; reduced motion swaps immediately. Duplicate clicks are ignored until the current write completes. Read responses started before a mutation cannot overwrite that mutation. Empty and unmatched results use the same empty-state component as Posts/Files. It updates after mutations; there is no permanent Refresh control, but failed reads retain a retry action. The editor provides live previews, custom field feedback, search, eight-item management pages, hide/show through the edit dialog, confirmed deletion, adjacent move controls and an editable order number. Enter or leaving the number field swaps the current link with the link at the selected position; other links keep their positions. While the number field is open, nonempty invalid values immediately show a red error state; an empty field shows it only after Enter. Entering a valid position clears the error, and Enter with an invalid value leaves the field open. Escape cancels the edit. The number field eases into and out of editing, and its row stays highlighted while editing. Clear search before reordering so the visible order is unambiguous. Cancel, the close button, Escape or a backdrop click closes a link dialog directly and discards unsaved edits, without an article leave confirmation or browser recovery copy. New Link remains available during list reads and ordering, except when the known collection has reached its limit. A draft can be edited or cancelled while another operation is pending; its Save action explains why submission must wait for a complete list or the current write. The limit is checked again before saving. A save in progress blocks duplicate submission and dialog closure. Save failures retain the form. A conflict requires closing the dialog (copy pending text first), leaving and re-entering the Links tab to read current data, then editing the current record. Writes use versions, and create retries reuse the dialog's request ID to avoid duplicate links after a lost response.

The collection is limited to 100 links, including hidden ones, to keep a single homepage read small and bounded. Management search and pagination operate on this same small collection. Public reads return only visible links, ordered by position and ID. Homepage SSR requests links alongside recent posts with no persistent cache. Navigation/reload reads current data; an already open page is not a live subscription.

Homepage link cards and the live preview reserve two lines each for titles and descriptions. Management rows show the title, description and destination on one line each, with ellipses for overflow; they keep status, order controls and More aligned in separate columns on wide screens. Empty descriptions display `No introduction provided.` in muted text. Long text wraps within its region and is clamped with an ellipsis instead of increasing card height or width. The homepage and live preview share the two-line title/description treatment. Cards do not open hover/focus tooltips, so reading or moving the pointer never covers adjacent content. Use Edit in Content Editor to read the complete title, description and destination. Full text remains in the document for assistive technology.

On wide screens the homepage shows four cards in one row. Smaller screens show two or one. Native horizontal scrolling and scroll snapping support touch, trackpads and keyboard focus. Mouse dragging scrolls the row and snaps to a nearby card on release; crossing the drag threshold suppresses the associated click so a drag does not open an external tab. Ordinary clicks and keyboard activation still open links. There are no previous/next buttons or reserved side gutters. The final viewport can overlap preceding cards to avoid empty fillers. Collections that fit do not enable mouse dragging. Reduced motion uses immediate positioning.

The color picker retains four theme-aware presets. Clicking Custom opens a compact, themed floating panel beside the button with a draggable saturation/brightness plane, hue/saturation/brightness sliders and a HEX input. The panel stays within viewport edges without resizing the edit dialog, uses subtle entrance and exit transitions, and respects reduced motion. All changes preview immediately; Escape or the close button dismisses only the color panel and restores focus to Custom. Clicking or focusing outside dismisses it without moving focus. Incomplete HEX input is not applied and resets to the last valid color on blur. Custom colors persist as six-digit HEX values and remain exact in both themes; preset colors continue to adapt to the theme. Preview, management rows and homepage cards share this behavior.

Migration `2026092201` preserves the four former static card descriptions as hidden, unconfigured templates. Add destinations and enable them in Links before expecting public cards to appear. Repeated startup/migration never recreates deleted templates. No destination URL is seeded.

API: `GET /api/links`; administrator-only `GET/POST /api/admin/links`, `PUT/DELETE /api/admin/links/:id`, and `POST /api/admin/links/:id/move`. All mutations require CSRF protection. Update/delete require the current version; moves require the current versions of the moved link and its adjacent neighbor or destination link, and commit atomically. Admin writes serialize briefly on the links table to keep ordering, collection limits and create replay checks consistent. Successful and failed reads inherit the application's no-store cache policy.


## Dialogs and controls

Content Editor deletion dialogs share an entrance and exit transition across posts, files, links and categories. Cancel, Escape, backdrop dismissal and successful deletion keep the dialog mounted until exit finishes; successful deletion also eases the backdrop blur away as the updated page appears. Background isolation and focus containment remain active during that interval. Closing preserves the displayed resource and message even when the parent clears its selection. Reopening cancels an obsolete exit, and reduced motion closes immediately. Failed or blocked deletions remain open. Focus returns to the invoking control, or to the resource panel when that control was deleted.

Posts, Files and Links use matching toolbar controls; All Posts and Cloud Drive share their search-field style. Submit with Enter or the search button; clearing the input takes effect only after submission. Enter during text composition does not submit.

Category management always targets the selected category. Pointer hover and keyboard navigation highlight options without changing the rename/delete target; an unavailable or unmanageable selection exposes no category management actions.

Links and Files dialogs share a modal surface. Their panels and backdrops enter and exit together; Cancel, the close button, Escape, backdrop clicks and successful saves use the same exit lifecycle. Focus and background isolation remain within the dialog until exit completes. Successful saves keep controls locked and retain the saving label throughout exit, while failures preserve entered values and allow retry. Backdrop dismissal requires a pointer press and click both on the backdrop, so dragging out of a field does not close the dialog. Dismissal discards unsaved edits without an article recovery confirmation. Reduced motion skips animation. File upload and preview dialogs also use this surface for consistent dismissal.

Selecting a category closes the dropdown with a transition while immediately removing it from interaction; reduced motion closes without transition.

Link save failures retain the draft and previous error during retries. A reserved feedback area prevents ordinary validation errors from resizing the centered dialog; Save keeps its label and appearance while disabled, with progress announced separately.
